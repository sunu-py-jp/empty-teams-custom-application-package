# Teamsカスタムアプリ インポート可否検証手順書

文書版：1.1（技術レビュー反映版）  
作成日：2026年9月30日  
対象：検証用パッケージの準備、管理者登録、任意のユーザー追加

> **現在の準備状態**  
> 同梱の `TeamsImportTest` フォルダーは、ZIP作成前の作業用ファイルである。`manifest.json`、`color.png`、`outline.png` の3ファイルを格納している。会社情報・URLは未設定のため、置換用の値を使用している。**未設定値を変更して検証するまでは、お客様へ配布・アップロードしない。今回の成果物にはTeams登録用ZIPを作成していない。** 実環境への登録・追加結果も未確認である。

## 1. 目的

当社が作成したTeamsアプリパッケージを、お客様のMicrosoft 365／Teams環境にインポートできるか確認する。

本検証では、業務画面、Bot、認証処理、外部API連携などのアプリケーション本体は実装しない。アプリの定義情報とアイコンを含む最小構成のZIPファイルを作成し、お客様環境での登録可否を確認する。必要な場合に限り、テストユーザーによる登録済みアプリの追加まで確認する。

### 1.1 検証の基本方針

- 当社は、本番用と区別した名称・アプリIDの検証専用パッケージを作成する。
- お客様のTeams管理者が、お客様の管理センターから登録する。
- **管理者登録だけを行う場合も、登録前後に利用対象を確認する。** 登録だけで全社員に利用可能になることがないよう、現在の管理方式と新規カスタムアプリの既定設定を事前確認する。
- 管理者登録だけの場合は、対象アプリを原則 `No one`（誰も利用できない）にする。ユーザー追加試験を行う場合は、指定したテストユーザーまたはテストグループだけに限定する。
- 登録、ユーザー追加、タブ表示、本番機能の動作を別々の確認項目として扱う。
- 全社員への公開や、全社員へのカスタムアプリ直接アップロード許可は前提としない。

### 1.2 本検証で確認できること

| 確認項目 | 内容 |
|---|---|
| 管理者によるインポート可否 | お客様のTeams管理センターから、当社作成のZIPを登録できるか |
| アプリ情報の登録 | アプリ名、マニフェスト由来のID、バージョンを確認できるか |
| 利用対象の管理 | 登録のみなら利用不可、追加試験を行うなら指定ユーザーに限定できるか |
| ユーザーによる追加可否 | 指定ユーザーが、登録済みアプリをTeamsに追加できるか（任意） |

### 1.3 本検証では確認しないこと

| 対象外の項目 | 理由 |
|---|---|
| 業務画面の正常表示 | 業務画面を実装しないため |
| Botの応答 | Botを定義・実装しないため |
| SSOやユーザー認証 | 認証機能を組み込まないため |
| Microsoft GraphなどのAPI呼び出し | API連携を実装しないため |
| バックエンドとの通信 | バックエンドを構築しないため |
| 本番アプリの権限・同意・接続要件 | 本番アプリでは構成や要求する権限が異なるため |

**成功が意味するのは、この検証用パッケージを対象環境に登録できたこと、または指定ユーザーが追加できたことである。本番アプリの機能が動作することを保証するものではない。**

## 2. 作成するパッケージの概要

### 2.1 Teamsアプリパッケージとは

Teamsアプリパッケージは、アプリの設定ファイルとアイコンなどをまとめたZIPファイルである。アプリ本体のプログラムやデータベースを格納してTeams上で実行するものではない。Web画面やBotの処理は別の場所で動作するため、パッケージ登録とアプリ本体の動作を切り分けて確認できる。[1]

### 2.2 今回の最小構成

アプリ名、説明、開発会社情報、検証用アプリID、バージョン、アイコン、個人用タブ1つを定義する。Bot、メッセージ拡張、SSO、追加API権限要求は定義しない。

### 2.3 ZIPと作業フォルダー

同梱成果物のうち、Teamsへ登録するZIPに入れるのは次の3ファイルだけである。

```text
TeamsImportVerification/
├── TeamsImportTest/         ← ZIP作成前の3ファイル
│   ├── manifest.json
│   ├── color.png
│   └── outline.png
└── docs/                    ← 手順書。Teams登録用ZIPには含めない
    └── Teamsカスタムアプリ_インポート可否検証手順書.md
```

上図は主要ファイルを示す。他に補助ファイルが同梱されていても、Teams登録用ZIPの対象には含めない。

| ファイル | 役割 |
|---|---|
| `manifest.json` | 名称、説明、アイコンの参照、タブなどを定義する |
| `color.png` | 192×192ピクセルのカラーアイコン |
| `outline.png` | 32×32ピクセル、透明背景に白い図柄のアイコン |

最終的に作成するZIPは、次のように直下へ3ファイルを格納する。

```text
TeamsImportTest.zip
├── manifest.json
├── color.png
└── outline.png
```

### 2.4 タブの参照先URL

個人用タブには、利用してよい既存のHTTPSページを設定する。登録確認だけのために業務用Webアプリを新規開発する必要はない。

ただし、通常のWebページはTeams内の埋め込みを許可していないことがある。また、Teamsタブの表示にはTeamsJSを読み込み、`app.initialize()`を呼び出すなどの要件がある。これらを満たさない既存ページは、Teams内で正常表示されない。[3]

**タブの表示は合格条件に含めない。表示エラーだけで登録失敗・追加失敗と判断せず、管理画面の登録状態またはユーザーの追加済み状態を確認する。**

画面表示まで確認する場合は、Teams向けHTMLページ、TeamsJS初期化、埋め込みを許可するHTTPヘッダー、HTTPS公開環境などを別途用意する。なお、今回もタブを開けば参照先HTTPSページへのアクセスは発生し得るため、使用するURLは事前に確認する。

## 3. 検証方法の区分

| 区分 | 操作する人 | 操作場所 | 確認すること |
|---|---|---|---|
| A. 管理者による登録 | お客様のTeams管理者 | Teams管理センター | 組織のカタログに登録できるか |
| B. 登録済みアプリの追加 | お客様のテストユーザー | Teamsクライアント | 登録されたアプリを指定ユーザーが追加できるか |
| C. ユーザーによる直接アップロード | お客様のテストユーザー | Teamsクライアント | 自分でZIPを取り込めるか |

### 3.1 今回の推奨範囲

まずAを行う。ユーザーへの提供まで確認する場合にBを続ける。Cはその運用が必要な場合だけ、別試験として行う。

Aだけの場合も、第7章の利用対象確認・制限まで実施する。Bを省略しても、利用対象の管理を省略してよいわけではない。

### 3.2 管理者登録とユーザーアップロードの違い

一般ユーザーによるカスタムアプリのアップロードが禁止されていても、管理者による登録経路は別に存在する。一般ユーザーにアップロードメニューがないことだけで、組織への導入ができないと判断しない。[5]

管理者登録の確認のために、全社員へZIPの直接アップロードを許可する必要はない。

## 6. 当社側の作業手順

### 6.1 手順1：同梱ファイルとアプリ情報を確認する

同梱の`TeamsImportTest`フォルダーを作業場所とする。既に用意されている3ファイルを編集・確認し、完成後にZIP化する。

| 項目 | 今回の値・方針 |
|---|---|
| アプリ名 | Teamsインポート確認 |
| 正式名称 | Teamsアプリ導入可否確認用 |
| マニフェストのアプリID | `aa718629-9efd-4f0f-adcd-92722db3161c` |
| アプリバージョン | `1.0.0` |
| マニフェストバージョン | `1.19` |
| 開発会社名 | 未設定。置換用マーカーを実際の会社名に変更する |
| 会社・規約・タブのURL | 未設定。`example.invalid`配下の値を実際のHTTPS URLへ変更する |
| Teams登録用ZIP | 未作成 |

上表のIDは、同梱`manifest.json`の`id`と一致することを確認する。

**同じアプリを修正する場合はIDを維持し、更新配布時に`version`を上げる（例：`1.0.0`→`1.0.1`）。別アプリとして新規登録する場合のみ新しいIDを使う。** マニフェストを変更した場合の版更新は公式スキーマでも示されている。[2]

今回の未設定値を確定させる作業は初回配布の準備であり、未登録であれば初回版は`1.0.0`としてよい。既に登録した版を変更して再配布する場合は、同じIDでバージョンを上げ、既存アプリの詳細画面から更新ファイルをアップロードする。[5]

別の検証アプリ用GUIDを新規発行する場合の例を示す。今回同梱のGUIDを利用する場合は実行不要である。

Windows PowerShell：

```powershell
[guid]::NewGuid().ToString()
```

macOSのターミナル：

```bash
uuidgen
```

### 6.2 手順2：未設定の会社情報・URLを置き換える

`TeamsImportTest/manifest.json`をエディターで開き、次の項目を変更する。

| JSONの項目 | 設定する内容 |
|---|---|
| `developer.name` | 実際の開発会社名。v1.19では32文字以内 |
| `developer.websiteUrl` | 開発会社・アプリの案内やサポートを提供するHTTPSページ |
| `developer.privacyUrl` | 当該検証に使用するプライバシーポリシーのHTTPSページ |
| `developer.termsOfUseUrl` | 当該検証に使用する利用条件のHTTPSページ |
| `staticTabs[0].contentUrl` | 使用が認められているタブ参照先のHTTPSページ |
| `staticTabs[0].websiteUrl` | ブラウザーで開く場合のHTTPSページ |
| `validDomains` | タブで使用する実際のドメイン。URL全体やパスは書かない |

`example.invalid`は未設定であることを示す置換用の値であり、実際の参照先として使わない。会社名、URL、ドメインが未設定のままZIP化・配布しない。

例として`contentUrl`が`https://teams-test.company.example/`なら、`validDomains`には`teams-test.company.example`を指定する。この記載例も実在の会社情報ではない。リダイレクトなどで別ドメインを読み込む場合は、そのドメインも確認する。

`developer.privacyUrl`と`developer.termsOfUseUrl`は、単に到達可能なページであればよいのではなく、それぞれの内容を提供するページを社内確認のうえ指定する。

### 6.4 手順4：アイコンを確認する

| ファイル名 | サイズ | 内容 |
|---|---|---|
| `color.png` | 192×192ピクセル | カラーアイコン |
| `outline.png` | 32×32ピクセル | 透明背景に白い図柄のアイコン |

画像形式はPNGとし、ファイル名をマニフェストの`icons`と一致させる。[2] 同梱アイコンをそのまま使用してよい。変更する場合も、画像サイズ・透過・白い図柄を維持する。

### 6.5 手順5：JSONとマニフェストを確認する

Windows PowerShellでは、`TeamsImportTest`フォルダーで次を実行するとJSON構文を確認できる。

```powershell
Get-Content -Raw -Encoding UTF8 .\manifest.json |
    ConvertFrom-Json |
    Out-Null
```

**JSONとして読み込めることは、Teams仕様への適合やお客様環境への登録成功を意味しない。** マニフェストのスキーマに対する確認と、実際の登録試験は別に行う。

エディターでv1.19スキーマを参照するか、Developer PortalのApp package editorでファイル更新時のエラーを確認する。Developer Portalはエラー付きの保存が可能なため、「読み込めた」「保存できた」だけを適合判定にしない。[4]

Developer Portalの別機能である「Publish → App validation」はTeams Store審査向けの検証であり、この個人用タブだけの登録試験の必須手順としない。

### 6.6 手順6：ZIP化前のチェックを行う

- [ ] `TeamsImportTest`直下に`manifest.json`、`color.png`、`outline.png`がある。
- [ ] `manifest.json.txt`などの意図しない拡張子になっていない。
- [ ] JSONをUTF-8で保存した。
- [ ] 会社名マーカー、`example.invalid`、その他の未設定値をすべて置換した。
- [ ] URLの用途と使用可否を確認し、実際のHTTPS URLを記載した。
- [ ] `validDomains`が実際の参照先ドメインと一致している。
- [ ] アプリIDが6.1の値と一致している。
- [ ] 更新配布の場合は同じIDを維持し、バージョンを上げた。
- [ ] アイコン名、PNG形式、画像サイズ、アウトラインの透過を確認した。
- [ ] 業務機能を持たない検証用アプリであることが説明に記載されている。
- [ ] JSON構文とマニフェストのエラーを確認した。
- [ ] 検証先の公開範囲・登録後の利用対象をお客様と確認した。

### 6.7 手順7：準備完了後にZIPを作成する

**今回の納品状態は、この手順を実行する前である。** 未設定値の置換と前項の確認が終わった段階で、以下のいずれかの方法を実行する。

Windows PowerShellでは`TeamsImportTest`フォルダーで実行する。

```powershell
Compress-Archive `
    -Path .\manifest.json, .\color.png, .\outline.png `
    -DestinationPath ..\TeamsImportTest.zip
```

macOSではターミナルで`TeamsImportTest`フォルダーへ移動してから実行する。

```bash
zip -X ../TeamsImportTest.zip manifest.json color.png outline.png
```

同名ZIPが既にある場合は、前の検証成果物として別名へ移動・保管してから作成する。既存ZIPに追加・更新する形で使い回さず、今回の3ファイルだけを格納したZIPを用意する。

ZIPを開き、3ファイルが直下にあることを確認する。次の構造は使わない。

```text
TeamsImportTest.zip
└── TeamsImportTest/         ← この余分な階層を作らない
    ├── manifest.json
    ├── color.png
    └── outline.png
```

手順書、README、検証記録、元画像などはTeams登録用ZIPに含めない。GUIで圧縮した場合も、親フォルダーやmacOSの付随ファイルが入っていないことを確認する。

### 6.8 手順8：可能なら自社環境で事前登録する

お客様へ渡すZIPと同じものを、自社Teams検証環境へ登録する。パッケージ不備とお客様側の制限を切り分けるために実施する。

| 確認結果 | 意味 |
|---|---|
| JSON構文エラーなし | JSONとして解析できた |
| スキーマ・編集ツール上でエラーなし | その検証方法でマニフェストの不備が検出されなかった |
| 自社Teamsに登録成功 | 自社環境で登録できた |
| お客様Teamsに登録成功 | お客様環境で登録できた |

前段の成功で後段の成功を確定させない。事前確認を実施できない場合は、未実施と明記する。自社環境でも利用対象を必要な範囲に制限する。

### 6.9 手順9：お客様へ渡す

| 共有物 | 内容 |
|---|---|
| 検証用ZIP | 完成した`TeamsImportTest.zip` |
| アプリ情報 | 名称、マニフェストの`id`、バージョン |
| 検証範囲 | Aのみ、A+B、必要ならC |
| 利用対象 | Aのみは原則No one。Bは指定テストユーザー／グループ |
| 対象外事項 | タブ表示、業務機能、Bot、SSO、API連携 |
| 操作手順 | 本手順書 |
| 事前検証結果 | JSON、スキーマ、自社登録の実施結果を区別して記載 |
| 結果の共有方法 | 登録情報、利用対象、追加状態、エラー全文など |

タブが表示されなくても、登録・追加に失敗したとは限らないことを事前に伝える。

## 7. お客様側の作業手順：管理者による登録

### 7.1 手順1：対象テナント、権限、管理方式を確認する

- [ ] 操作対象が正しいお客様テナントである。
- [ ] Teamsアプリを管理できるアカウントである。
- [ ] 社内で必要な登録・検証の確認が済んでいる。
- [ ] 受領したZIPの名称、マニフェストID、バージョンを把握している。
- [ ] 今回の範囲がAのみか、Bまで含むか確定している。
- [ ] アプリ中心の管理の利用状況と、統合アプリ管理（UAM）への移行状況を確認した。
- [ ] 登録直後の既定の利用対象と、対象を限定する方法を確認した。

アプリ中心の管理と、Teams／Microsoft 365両管理センターをまたぐUAMは、同じ確認項目として扱わない。それぞれ現在の環境を確認する。[6][10]

### 7.2 手順2：アップロード前に既定の公開範囲を確認する

Teams管理センターで、概ね次の場所を確認する。

```text
Teamsアプリ → アプリを管理 → アクション → 組織全体のアプリ設定
```

カスタムアプリについて、利用可能なアプリをユーザーが既定でインストール・利用できる設定と、新しく登録するアプリの扱いを確認する。[6][11]

| 今回の検証 | 登録後に設定・確認する利用対象 |
|---|---|
| A. 管理者登録のみ | 原則`No one`。管理者はカタログへの登録情報を確認する |
| A+B. 登録とユーザー追加 | 指定したテストユーザー／テストグループのみ |

新規アプリが既定で全員に利用可能になる場合は、**アップロード前に**お客様の管理者が限定方法を決める。既定設定を一時変更する場合は、他のアプリへの影響と変更前の値を確認し、必要な反映を待つ。登録直後に個別設定を変更すれば、最初から公開されなかったことになるとは扱わない。

必要な限定方法が確立できていない場合は、登録操作を保留してお客様の運用担当者と調整する。検証のために無条件で組織全体のポリシーを緩和しない。

### 7.3 手順3：Teams管理センターからアップロードする

お客様管理者が[Teams管理センター](https://admin.teams.microsoft.com/)を開く。

```text
Teamsアプリ → アプリを管理 → 新しいアプリをアップロード
```

画面によっては［アクション］内にアップロード操作がある。文言や配置は現在の画面に合わせて読み替える。[5]

当社から受領した`TeamsImportTest.zip`を、解凍せずに選択してアップロードする。確認画面が出た場合は、検証用アプリの名称を確認して進める。

### 7.4 手順4：登録後ただちに利用対象を確認する

対象アプリの詳細を開き、次を確認・保存する。

```text
対象アプリ → ユーザーとグループ → 利用可能性（Availability）
           → 利用可能性を編集 → No one または特定のユーザー／グループ
```

Aのみの場合は`No one`、Bまで実施する場合は指定テストユーザー／グループのみとする。保存後の値と時刻を記録し、意図せず`Everyone`になっていないことを確認する。反映時間は第8.7項を参照する。

アプリ中心の管理が利用されていない環境では、現在のアプリ状態・アクセス制御方式で同等の範囲に制限する。本検証のためだけに管理方式の移行は行わない。

### 7.5 手順5：Microsoft 365側の設定との整合を確認する

| UAMの状態 | 確認方法 |
|---|---|
| 移行済み | Teams管理センターまたはMicrosoft 365管理センターの統合アプリから管理する。対象アプリの利用対象が意図どおりになっていることを確認する |
| 未移行 | Teams管理センターに加え、対象アプリを管理するMicrosoft 365管理センターの［統合アプリ］側も確認し、許可・ブロックなどの設定を整合させる |
| 不明 | お客様管理者が移行状況と対象アプリの管理場所を確認し、記録する |

未移行環境では、一方の管理センターだけの設定で他方にも反映済みと判断しない。対象アプリの表示状況と管理方式に合わせて確認する。すべての環境で両方の管理センターに同じ操作を繰り返す必要がある、という意味ではない。[6][10][11]

### 7.6 手順6：名称、ID、バージョンを照合する

| 確認項目 | 期待する内容 |
|---|---|
| アプリ名 | 受領したアプリ情報と一致する |
| External app ID／外部アプリID | `manifest.json`の`id`と一致する |
| バージョン | 受領したアプリバージョンと一致する |
| 説明 | 業務機能のない検証用である旨を確認できる |
| 利用対象 | No one、または指定テストユーザー／グループのみ |

**マニフェストの`id`と比較するのは、マニフェスト由来のExternal app IDである。** Teamsのカタログで生成されたApp IDは別の値になることがある。Microsoft Graphの`teamsApp`でも`externalId`とカタログの`id`は区別されている。[8][9]

画面で単に「App ID」と表示されている場合は、その項目がどちらのIDかを確認する。値が異なるだけで誤登録と判定しない。External app IDが見つからない場合は、［アプリを管理］の列設定でExternal app ID列を表示するか、対象カスタムアプリの詳細画面を確認する。[9] 未確認のままID一致と記録しない。Graph APIの実装は本試験に不要である。

### 7.7 管理者によるインポート試験の合格条件

次の3条件を満たせば、登録そのものを成功とする。

1. ZIPのアップロードが完了した。
2. 管理センターで対象アプリを確認できた。
3. 名称、マニフェスト由来ID、バージョンが配布情報と一致した。

加えて、本手順の運用上の完了条件として、利用対象を想定どおりに制限し、その状態を記録する。**登録は成功していても利用対象の確認が未完了なら、「登録成功／利用対象確認中」と分けて報告する。**

登録成功は、すべてのユーザーが利用可能という意味ではない。Bを実施する場合は次章へ進む。

## 8. お客様側の作業手順：テストユーザーによる追加

本章はBを行う場合に実施する。

### 8.1 手順1：利用対象を確認する

第7章で保存した利用対象が、指定したテストユーザーまたはテストグループになっていることを確認する。Aで`No one`に設定した後にBを行う場合は、この段階でテスト対象に限定して変更する。

アプリ中心の管理では、［ユーザーとグループ］→［利用可能性］→［利用可能性を編集］→［特定のユーザーまたはグループ］で対象を設定する。[6]

### 8.2 テストアカウントの方針

| 項目 | 方針 |
|---|---|
| 利用対象 | 指定テストユーザー／テストグループ |
| テストアカウント | お客様テナント内のTeams利用ユーザー |
| 当社のゲストアカウント | 初回試験の前提にしない |
| 全社員への公開 | 原則不要 |

「特定のユーザーまたはグループ」の設定では、ゲストを対象に指定しても利用できない制約がある。まずテナント内ユーザーで確認する。[6]

### 8.3 手順2：テストユーザーでTeamsを開く

対象ユーザーでTeamsにサインインし、現在選択している組織が検証対象テナントであることを確認する。複数組織を切り替えている場合は特に注意する。

### 8.4 手順3：登録済みアプリを探す

Teamsのアプリ画面から、組織用アプリの一覧や名称検索で対象を探す。[5]

```text
Teams → アプリ → 組織向けに作成 → Teamsインポート確認
```

文言や配置はTeamsの表示に合わせて読み替える。見つからない場合は第8.7項の反映待ちと利用対象を確認する。

### 8.5 手順4：追加する

対象アプリを選んで［追加］を実行する。Teamsの［アプリを管理］などで追加済みの状態を確認し、証跡を保存する。

追加操作に伴ってタブが開き、画面表示に失敗する場合も、追加済み状態は別に確認する。タブ表示エラーだけでBを失敗としない。

### 8.6 ユーザー追加試験の合格条件

1. 対象ユーザーが検証用アプリを見つけられた。
2. 追加操作を実行できた。
3. ユーザーのTeamsで追加済みと確認できた。

タブの正常表示は合格条件に含めない。

### 8.7 反映待ちの扱い

利用可能性の変更には最大24時間、まれにクライアントへの反映に最大6日かかる場合があるとMicrosoftは案内している。[6] この時間は利用対象変更の反映に関する目安であり、すべてのエラーを待つだけで解消できるという意味ではない。

直後に表示されない場合は、対象ユーザー・グループ、対象組織、保存された設定、アプリの許可状態、UAMの管理方式を確認する。設定変更時刻、再確認時刻、表示状態を記録し、**「反映待ち」**として扱う。即時に失敗と断定したり、反映待ち中にアプリを繰り返し新規登録したりしない。

24時間後も反映されない場合は、お客様管理者が設定やサービス状況を再確認する。必要に応じて問い合わせし、再確認期限を決める。6日間待機を必須条件にするものではない。

## 9. 任意の追加試験：一般ユーザーによるZIPの直接アップロード

### 9.1 実施する条件

一般ユーザーが自分でZIPを取り込む運用を想定している場合だけ、Cとして実施する。AやBとは別の結果を記録する。

### 9.2 管理者側の事前確認

次をお客様管理者が確認する。[5][7]

- 組織側のカスタムアプリアップロードに関する設定。
- テストユーザーに割り当てられたアプリセットアップポリシー。
- 当該ポリシーの［カスタムアプリをアップロード］設定。

必要な場合は、テストユーザーだけに許可する。アプリの「利用可能性」と、ユーザーの「直接アップロード許可」は別の管理項目として扱う。全社員への設定変更を前提とせず、禁止されている運用を検証のために無条件で許可するよう求めない。

### 9.3 ユーザー側の操作

```text
Teams → アプリ → アプリを管理 → アプリをアップロード
      → カスタムアプリをアップロード → TeamsImportTest.zip → 追加
```

画面表示に合わせて読み替える。個人用タブの追加先として、テストユーザー自身の個人スコープを確認する。

### 9.4 判定方法

| 状況 | 判定・対応 |
|---|---|
| ZIPを選択して追加済みになった | C成功 |
| アップロードメニューがない | 適用ポリシーなどを確認する |
| ZIP選択後にエラーになる | エラー全文を記録し、パッケージと環境の問題を切り分ける |
| 組織方針で禁止されている | C対象外、または運用上利用不可として記録する |
| 設定変更がまだ反映されていない | 反映待ちとして再確認時刻を記録する |

直接アップロードできないことと、管理者が組織に登録できないことは同義ではない。

## 11. トラブル時の切り分け

| 発生事象 | 主な確認内容 | 注意点 |
|---|---|---|
| アップロード操作が見つからない | 操作者の権限、管理センター、UI配置 | パッケージ不備とは限らない |
| ZIPが受け付けられない | 直下の3ファイル、JSON、スキーマ、アイコン、未設定値、エラー文 | エラー全文を記録する |
| IDが一致しないように見える | External app IDかカタログ側App IDか | マニフェストIDとカタログIDを直接比較しない |
| 名称・バージョンが想定と違う | 配布ZIPとmanifest、更新対象 | 別版や別アプリを選択していないか確認する |
| 同じIDの更新が受け付けられない | バージョン更新、既存アプリの更新操作 | IDを毎回変えて回避しない |
| 管理画面にあるがユーザーに見えない | 利用対象、対象組織、UAM状態、設定保存時刻 | Aは成功している可能性がある |

| 見えるが追加できない | 利用対象・許可設定・エラー全文 | 登録成功と追加成功を分ける |
| 追加できたがタブが表示されない | 追加済み状態、埋め込み・TeamsJSの要件 | 本試験のタブ表示は対象外 |
| 直接アップロードのメニューがない | 組織設定、セットアップポリシー | Aも禁止とは判断しない |

| 想定より広い利用対象になっている | 登録時の既定、アプリ個別の保存値、両管理センター | 利用対象を是正し、登録結果と別に記録する |

## 12. 検証終了後の対応

お客様の運用方針に従い、次を行う。

1. 検証用アプリを残すか削除するか決める。
2. 不要なら管理者が管理センターから削除する。残すなら利用対象をNo oneなど必要な範囲に限定する。
3. テストユーザーに追加したアプリが不要なら、ユーザー側でも削除する。
4. 一時変更した既定設定、ポリシー、利用対象を変更前の状態へ戻す。既存アプリへの影響も確認する。
5. 必要な管理センターの状態と反映を確認し、結果を記録する。
6. 使用したZIP、アプリ情報、検証記録、証跡を合意した場所に保管する。

本番アプリ導入時は本番用パッケージで再検証する。Bot、SSO、追加権限、外部通信先などを組み込む場合は、今回対象外の承認・接続・動作条件を別途確認する。

## 13. 最小限の実施内容

### 当社側

1. 同梱`TeamsImportTest`の会社名・URL・ドメインを実値に変更する。
2. 検証用アプリID、バージョン、JSON、スキーマ、アイコンを確認する。
3. 3ファイルをZIP直下へ格納する。
4. ZIPとアプリ情報、本手順書をお客様へ渡す。

### お客様側

1. テナント、権限、管理方式、新規カスタムアプリの既定公開範囲を確認する。
2. 想定する利用対象を確保して、管理者がZIPをアップロードする。
3. 登録後の利用対象を確認し、Aのみなら原則No oneにする。
4. 管理画面で名称、External app ID、バージョンを照合する。
5. 結果を記録し、検証後の後片付けを行う。

Bを実施する場合だけ、指定テストユーザーの追加確認を続ける。**この最小検証のために、新しいAzure環境、Bot、認証処理、API、データベースを構築する必要はない。**
